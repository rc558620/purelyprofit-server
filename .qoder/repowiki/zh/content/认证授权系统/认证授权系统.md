## 简介
本文件面向认证授权系统的使用者与维护者，系统性阐述基于 JWT 的认证机制、权限控制模型与子账户（Store Sub-Account）安全策略。文档从整体架构到关键组件逐层展开，覆盖认证流程、Token 生成与验证、权限继承与校验、子账户登录与限制等主题，并提供与数据库、Redis 缓存、装饰器与守卫等组件的集成说明，帮助初学者快速上手，同时为资深开发者提供足够的技术深度。

**重大安全更新** 认证系统实施了全面的安全增强措施，重点解决了跨租户访问防护问题。AuthAccountLookupService现在能够检测手机号或登录账号关联多个用户的情况，有效防止跨门店数据污染。JWT策略和会员解析服务增强了token处理和错误处理机制，确保在复杂的多租户环境下仍能保持严格的数据隔离。这些安全增强通过精确的用户身份验证、严格的权限匹配策略和详细的安全日志记录，显著提升了系统的整体安全性。

## 核心组件
- **统一认证服务**：AuthProductAuthService 提供多产品范围的统一认证接口，支持验证码发送、用户注册、登录、密码管理等功能。
- **封禁检查服务**：AuthBanGuardService 专门负责用户封禁状态检查，基于门店维度进行封禁判断，支持缓存优化和批量查询。
- **会员解析与缓存服务**：AuthMembershipResolverService 负责会员信息解析、权限计算、缓存管理和历史数据修复，现已增强跨租户访问防护。
- **员工激活工作流服务**：AuthStaffActivationService 处理邀请员工激活、席位配额管理和缓存失效逻辑。
- **验证码服务**：AuthCodeService 负责验证码的生成、存储、验证和清理，支持注册、登录和密码重置场景。
- **短信服务**：AuthSmsService 处理短信验证码的发送，支持注册、登录和密码重置短信通知。
- **主认证控制器与服务**：负责登录、注册、密码操作、会话管理、能力查询等入口与业务逻辑。
- **purely-club 认证模块**：专为个人端用户设计的独立认证系统，支持独立的注册、登录、密码找回等功能。
- **purely-pulse 认证模块**：专为开发者设计的认证系统，现重构为轻量级实现，依赖主认证模块提供核心认证能力。
- **JWT 守卫与策略**：负责解析请求中的 JWT，校验签名与有效期，并注入当前用户上下文，现已增强token处理和错误处理机制。
- **权限守卫与装饰器**：用于方法级权限校验与子账户访问阻断。
- **子账户服务**：提供子账户的读取、槽位管理与登录辅助能力。
- **用户资料服务**：提供用户资料查询、更新头像、昵称更新、实名认证等功能。
- **注册门店创建服务**：提供注册后的门店创建功能，支持完整的注册闭环流程。
- **基础设施**：Prisma 数据库访问、Redis 缓存、全局配置。

## 架构总览
认证授权系统采用"控制器-服务-守卫-策略-装饰器"的分层设计，结合数据库与缓存完成身份认证与权限控制。JWT 作为无状态凭证贯穿整个流程；权限控制通过守卫与装饰器在路由层进行拦截与判定；子账户登录由专门的服务与守卫协同处理，确保主账户与子账户的边界清晰。

**重大安全架构更新** 经过安全增强后，认证系统现在具备强大的跨租户访问防护能力。AuthAccountLookupService实现了智能的多用户冲突检测机制，能够在登录时识别手机号或登录账号关联多个用户的情况，立即阻止潜在的跨门店数据污染。JWT策略增强了token验证的安全性，会员解析服务采用了严格的匹配策略，确保即使在复杂的迁移场景下也能保持数据隔离。

### 跨租户访问防护机制
**重大安全更新** AuthAccountLookupService实现了全面的跨租户访问防护，能够有效检测和防止跨门店数据污染。

- **多用户冲突检测**
  - 在手机号登录时，系统会检查该手机号是否关联了多个不同的用户ID
  - 如果发现跨租户的手机号关联，立即拒绝登录并抛出ConflictException
  - 详细的警告日志记录包含具体的手机号、匹配的员工数量和涉及的不同用户数量

- **登录账号冲突检测**
  - 对于自定义登录账号，同样执行多用户冲突检测
  - 确保每个登录账号只能关联单一用户，防止账号混淆
  - 提供友好的错误消息指导用户联系管理员处理

- **开发者模式特殊处理**
  - 开发者模式的手机号登录也应用相同的跨租户防护
  - 确保开发环境下的数据安全性和隔离性

### SMS冷却与速率限制

**更新** 新增SMS冷却功能，使用Redis setIfAbsent操作实现精确的速率限制，防止恶意刷短信攻击。

- **冷却机制原理**
  - 使用Redis的setIfAbsent操作实现原子性的冷却标记
  - 基于场景、产品范围和手机号的组合键进行独立冷却
  - 通过NX选项确保同一时间只有一个请求能够获取冷却令牌

- **支持的冷却场景**
  - 注册场景：`auth:sms-cooldown:register:{productScope}:{phone}`
  - 登录场景：`auth:sms-cooldown:login:{productScope}:{phone}`
  - 密码重置场景：`auth:sms-cooldown:password-reset:{productScope}:{phone}`
  - 登录或注册场景：`auth:sms-cooldown:login_or_register:{productScope}:{phone}`

- **冷却配置**
  - 默认冷却时间为60秒（可通过配置调整）
  - 支持禁用冷却功能（冷却时间为0）
  - 每个场景独立配置，避免相互影响

- **异常处理**
  - 冷却期间返回HTTP 429状态码
  - 提供友好的错误消息："短信发送过于频繁，请 {seconds} 秒后再试"
  - 冷却结束后自动释放锁，允许下次发送

## 性能考虑
- **验证码缓存优化**
  - 使用 Redis 缓存验证码，避免重复生成和发送
  - 设置合理的过期时间，平衡安全性和性能
  - 支持测试环境直接显示验证码，提高开发效率

- **短信服务降级**
  - 短信发送失败时自动回滚缓存操作，确保数据一致性
  - 提供日志记录，便于监控和故障排查
  - 支持异步发送，避免阻塞主线程

- **Token 缓存与降级**
  - 对频繁访问的用户能力进行缓存，降低数据库压力
  - 在缓存不可用时采用降级策略
  - 参考：[redis.service.ts:1-200](file://src/redis/redis.service.ts#L1-L200)、[auth-capability.service.ts:1-200](file://src/purely-profit/auth/auth-capability.service.ts#L1-L200)。

- **权限判定优化**
  - 将权限集合预计算并按作用域分组，减少运行时聚合成本
  - 参考：[subject-capability.service.ts:1-200](file://src/purely-profit/access-control/subject-capability.service.ts#L1-L200)。

- **子账户登录节流**
  - 通过槽位服务限制并发登录数量，避免资源争用

- **模块依赖优化**
  - **重大更新** 通过 AuthModule 集中管理认证服务，减少模块间重复依赖

  - 统一的模块结构提高了代码维护性和性能表现

- **多产品范围优化**
  - 各认证范围独立缓存，避免跨范围数据污染
  - 开发者白名单缓存，减少配置查询开销

- **SMS冷却性能优化**
  - **更新** Redis setIfAbsent操作是原子性的，避免竞态条件
  - 冷却键使用短TTL，减少内存占用
  - 支持禁用冷却功能，满足特殊场景需求
  - 独立冷却周期避免场景间的相互影响

- **请求频率限制优化**
  - **更新** Throttle装饰器提供统一的请求频率限制
  - 基于Redis的分布式限流，支持高并发场景

- **用户资料缓存优化**

## 故障排除指南
- **验证码相关问题**
  - 现象：验证码发送失败或无法接收
  - 排查：检查短信服务配置、网络连接、Redis 缓存状态
  - 参考：[auth-code.service.ts:55-64](file://src/purely-profit/auth/auth-code.service.ts#L55-L64)、[auth-sms.service.ts:25-53](file://src/purely-profit/auth/auth-sms.service.ts#L25-L53)

- **Token 无效或过期**
  - 现象：请求被拒，提示鉴权失败。
  - 排查：确认 Token 是否正确携带、是否在有效期内、签名算法与密钥是否一致。
  - 参考：[jwt.strategy.ts:1-200](file://src/purely-profit/auth/strategies/jwt.strategy.ts#L1-L200)、[auth.constants.ts:1-41](file://src/purely-profit/auth/auth.constants.ts#L1-L41)。

- **权限不足**
  - 现象：方法级权限校验失败。
  - 排查：核对装饰器声明的权限集合与用户实际能力，检查主体能力计算逻辑。
  - 参考：[require-permissions.decorator.ts:1-200](file://src/purely-profit/access-control/decorators/require-permissions.decorator.ts#L1-L200)、[permissions.guard.ts:1-200](file://src/purely-profit/access-control/guards/permissions.guard.ts#L1-L200)。

- **子账户被阻断**
  - 现象：子账户访问被拒绝。
  - 排查：确认目标接口是否使用了阻断装饰器或守卫，必要时切换为主账户登录。
  - 参考：[block-sub-account.decorator.ts:1-200](file://src/purely-profit/access-control/decorators/block-sub-account.decorator.ts#L1-L200)、[sub-account-block.guard.ts:1-200](file://src/purely-profit/access-control/guards/sub-account-block.guard.ts#L1-L200)。

- **数据不一致**
  - 现象：权限或能力与预期不符。
  - 排查：检查数据库与缓存一致性，必要时清理缓存并重算能力。
  - 参考：[prisma.service.ts:1-200](file://src/prisma/prisma.service.ts#L1-L200)、[redis.service.ts:1-200](file://src/redis/redis.service.ts#L1-L200)。

## 结论
本认证授权系统以 JWT 为核心凭证，结合守卫与装饰器实现细粒度的权限控制，并通过主体能力服务构建可扩展的权限继承模型。经过重大安全增强后，系统现在具备了强大的跨租户访问防护能力，能够有效防止数据污染和安全漏洞。

**重大安全更新总结** 
- **跨租户访问防护**：AuthAccountLookupService实现了智能的多用户冲突检测机制，能够在登录时识别手机号或登录账号关联多个用户的情况，立即阻止潜在的跨门店数据污染
- **JWT策略增强**：JwtStrategy增强了token验证的安全性，改进了错误处理机制，并集成了session版本检查
- **会员解析服务强化**：AuthMembershipResolverService采用了严格的匹配策略，确保即使在复杂的迁移场景下也能保持数据隔离
- **安全日志记录**：所有跨租户访问尝试都记录了详细的警告日志，便于安全审计和问题排查

这些安全增强通过精确的用户身份验证、严格的权限匹配策略和详细的安全日志记录，显著提升了系统的整体安全性。系统现在能够有效防止跨租户数据污染，保护多租户环境下的数据安全。

purely-club 和 purely-pulse 认证模块通过独立的认证入口实现了产品范围的完全隔离，既保证了各业务线的独立性，又保持了统一的认证体验。purely-pulse 认证模块已成功重构为轻量级实现，通过依赖注入的方式复用主认证模块的核心能力，简化了模块结构，提高了代码复用率和维护性。

子账户体系通过登录服务、槽位服务与阻断守卫形成闭环，既保证灵活性又强化安全边界。配合数据库与缓存的合理使用，系统可在保证安全性的同时兼顾性能与可维护性。新的安全架构为未来的功能扩展和维护提供了更好的基础。
