| `src/purely-club/stores/club-store-access.service.ts` | `invalidateAccessibleStoresCache` 由 private 转 public |

**三条设计边界**（核验重点）：

1. **不触发账号合并** —— 新号已属于其他账号时**直接拒绝**；
2. **只校验新号** —— 用户换号后旧号已收不到短信，无法校验旧号；
3. **按 `clubUserId` / 门店范围定位档案，绝不跨门店按 `phone` 更新** ——
   旧号是真实号码，可能同时属于其他用户，无门店限定的 `phone` 更新会串改他人档案。

**同步方法 `syncPhoneAcrossProfiles` 的定位方式**（两张表不同，这是事故后的最终形态）：

| 表 | 定位 | 原因 |
|---|---|---|
| `MarketingCustomer` | `clubUserId` | 有该列，且有 `(storeId, clubUserId)` 唯一约束 |
| `Member` | `storeId IN (该用户有档案的门店)` + `phone = 旧号` | **既无 `clubUserId`，`customerId` 在现存数据里也全为 null** |

同时同步**自动生成的展示名**（`纯利会员XXXX`），仅当名字恰为自动生成值时才改
（不覆盖商家在 purelyProfit 手动改过的名字）。

```bash

npx prisma migrate status                                   # phone_rebind_at 迁移应为已应用
```

**要看的关键用例名**（若名字对不上说明代码没落到这版）：

- `Member 按「该用户有档案的门店 + 旧号」定位，不依赖 customerId`
- `Member 定位必须限定门店，否则会串改其他用户的档案`
- `同步自动生成的展示名 —— 否则商家端一直显示旧号后 4 位`
- `新手机号已属于其他账号 → 拒绝，且绝不触发账号合并`
- `冷静期内重复换绑被拒绝，并告知剩余天数`

### 1.2 换绑事故的修复（本次最重要的部分）

**首次真机验证暴露两个 bug，均已修复并补了回归测试。**

**① 换绑后「以前加入过的门店消失」**

根因：`syncPhoneAcrossProfiles` 原先按 `Member.customerId` 定位要更新的档案，
而 **`members.customer_id` 在库中全为 `null`**（该列是「可选、兼容历史数据」，从未被填充）
→ 更新命中 **0 条** → `Member.phone` 留在旧号 → 新 token 用新号匹配不到门店 → **0 个门店**。

修复：改按「该用户有档案的门店 + 旧号」定位（见 1.1 的定位表）。

> **教训（值得核验时留意）**：原先的单测断言的是**实现者假设的正确 WHERE 子句**
> （`customerId`），而不是数据库的真实形态，所以一路绿灯。
> 新增的 e2e `test/club-rebind-phone.e2e-spec.ts` **刻意把 `Member.customer_id` 造成 null**
> 来复现线上形态——它对该 bug 会失败。

**② 商家端展示名没变**（「纯利会员4011」应为「纯利会员4010」）

修复：换绑时一并同步自动生成的 `name`。

## 4. 退出登录 dev-only + 生产环境移除登录页（批次 4 修正）

**业务决定**：C 端身份由微信静默登录决定，退出登录后下次进入会被静默登回——
既无意义，又必须配套一个「能回来」的显式登录入口。故：

| | 生产环境 | 开发环境 |
|---|---|---|
| 退出登录入口 | 不渲染 | 渲染 |
| `markManualLogout` 调用 | **不可达**（全项目只剩退出登录这一处调用） | 可达 |
| 跳登录页（4 处） | **全部空操作** | 正常跳转 |
| 访问不到受限资源时 | 原地失败，下次静默登录自动恢复 | 跳登录页便于调试 |

**实现：一个受门禁保护的统一出口**

```ts
// purelyClub/src/utils/routeGuard.ts
const SHOW_LOGIN_PAGE = process.env.NODE_ENV !== 'production'

export const goToLoginPage = async (): Promise<boolean> => {
  if (!SHOW_LOGIN_PAGE) return false   // 生产：空操作
  await Taro.reLaunch({ url: LOGIN_PAGE_URL })
  return true
}
```

**4 个跳转点全部改走它**（核验时可 grep 确认没有裸 `Taro.reLaunch` 跳登录页）：

| 位置 | 生产行为 |
|---|---|
| `routeGuard.redirectToLoginIfNeeded`（401 + **18 个页面**的守卫） | 空操作 |
| `app.tsx` 的 `handleScanEntry`（未登录扫码） | 空操作 |
| `scanEntryDeps` 的 `redirectToLoginIfManuallyLoggedOut` | 空操作 |
| `useProfileController` 的退出登录 | 空操作（且入口不渲染） |

**核验命令**

```bash

# 应只剩 1 处（useProfileController 的退出登录）
grep -rn "markManualLogout()" src/ | grep -v __tests__
# 应只剩 routeGuard.ts 内部一处 reLaunch（在 goToLoginPage 里）
grep -rn "Taro.reLaunch({ url: LOGIN_PAGE_URL" src/ | grep -v __tests__

npx vitest run src/utils/__tests__/routeGuard.test.ts        # 期望 9 例通过
npx vitest run src/pages/loginPkg/bindPhone                  # 期望 5 例通过
npx vitest run src/pages/profile/__tests__/ProfilePage.test.tsx   # 期望 15 例通过
```

**同步改掉的 bindPhone 分支**：绑手机号页的「返回」原先在非确认订单页进入时会
**退出登录并跳登录页**，现已统一为直接返回上一页（栈底则回首页）。
