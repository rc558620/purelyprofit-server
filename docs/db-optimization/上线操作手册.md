# DB 优化上线操作手册

> **用途**：本文档是 DB 优化（I1~I9）全部改动的服务器端执行手册。用户登录服务器后，按步骤顺序逐条执行即可。
>
> **来源**：I1~I10 实施摘要（`docs/db-optimization/实施/notes.md`）+ 分析阶段 S1~S9（`docs/db-optimization/notes.md`）+ 仓库源码核实。
>
> **服务器环境**：单台 8 核 16G，应用 + PostgreSQL + Redis 同机部署。域名备案中，**尚未上线，无生产数据**。
>
> **前提**：应用代码（I1~I9 的全部 diff）已合并到主分支并已 `pnpm run build`，部署目录 `/opt/purelyprofit-server` 下的 `dist/` 已是最新构建产物。
>
> **执行原则**：
> 1. 每一步都包含「执行命令 / 预期输出 / 验证命令 / 失败处置」四要素。
> 2. 每一步开头标注执行窗口：**可在线** / **需低峰期** / **需停服**。
> 3. 标注 ⚠️ 的步骤为「本步失败必须停止，不要继续下一步」。
> 4. 凡涉及服务器实际状态（PG 版本、max_connections、磁盘空间等），本文档标为「待用户确认」，不假设。

## 上游矛盾说明

在开工前，发现上游结论之间有一处需要用户知晓的差异：

| 项目 | I1 摘要 | I2 摘要 | 说明 |
|------|---------|---------|------|
| `max_connections` | 推荐 pgMax=100（PG 默认值，无需改 postgresql.conf） | 保持默认 100，与应用侧 `DATABASE_PG_MAX_CONNECTIONS=100` 对齐 | **无矛盾**，两处一致 |
| 连接池预算 | workers=4, poolMax=20, 总连接 4×20=80 | 同上 | 一致 |
| 归档保留窗口 | I9 代码默认 365 天（`configuration.ts` 默认值） | I3 推荐 6 个月（180 天），标注「待拍板」 | 代码默认值 365 天 ≠ I3 推荐值 180 天。**本手册以代码实际默认值 365 天为准**，如需改为 180 天，请在 `production.env` 中设置 `APP_ARCHIVE_SALE_ORDER_ITEMS_RETENTION_DAYS=180` |

> ⚠️ **请确认**：归档保留窗口是 365 天（代码默认）还是 180 天（I3 推荐）？确认后在 `production.env` 中显式设置，避免歧义。

## 第 0 步：前置确认（需停服前执行）

> **执行窗口**：可在任何时间执行，但必须在第 1 步之前全部完成。
>
> **目的**：确认服务器实际状态与上游假设一致，排除环境差异导致后续步骤失败。

### 0.1 PostgreSQL 版本确认

**执行命令**：

```bash
sudo -u postgres psql -c "SELECT version();"
```

**预期输出**：

```
                                                  version
-------------------------------------------------------------------------------------------------------------
 PostgreSQL 17.x on x86_64-pc-linux-gnu, compiled by gcc (Debian ...) x, 64-bit
(1 row)
```

**验证**：输出中包含 `PostgreSQL 17`。

**失败处置**：
- 若版本不是 17（如 15/16）：I2 的参数推演基于 PG 17，部分参数名或默认值可能不同。**停止执行，先确认兼容性**。
- 若无法连接 psql：确认 postgres 服务是否运行 `sudo systemctl status postgresql`。

- [ ] 已确认 PostgreSQL 版本为 17

### 0.2 max_connections 实际值确认

**执行命令**：

```bash
sudo -u postgres psql -c "SHOW max_connections;"
```

**预期输出**：

```
 max_connections
-----------------
 100
(1 row)
```

**验证**：值为 `100`（PG 默认值），与 I1/I2 假设一致。

**失败处置**：
- 若值 ≠ 100：说明 `postgresql.conf` 已被修改过。需要确认该值的由来，并相应调整 `DATABASE_PG_MAX_CONNECTIONS` 环境变量使其与 PG 实际值一致。**不要直接改回 100**——先确认修改原因。

- [ ] 已确认 max_connections = 100

### 0.3 磁盘剩余空间确认

**执行命令**：

```bash
df -h /var/lib/postgresql
```

**预期输出**（示例）：

```
/dev/sda1        50G   15G   33G  32% /var/lib/postgresql
```

**验证**：剩余空间 ≥ 10GB（I4/I5 索引重建 + I9 归档表，预估增量 < 5GB，留 2 倍余量）。

**失败处置**：
- 若剩余空间 < 10GB：清理旧日志 / 旧备份后再继续。
- 若不确定归档表将占多大空间：sale_order_items 归档表会随时间增长，保留 365 天热数据意味着 6 个月以上的数据会迁入归档表。当前无生产数据，首次执行归档任务迁移量为 0。

- [ ] 已确认磁盘剩余 ≥ 10GB

### 0.4 当前数据库连接数确认

```bash
sudo -u postgres psql -c "SELECT count(*) FROM pg_stat_activity;"
```

**预期输出**：

```

-------

```

- [ ] 已确认无长事务 / 备份任务

## 第 1 步：PostgreSQL 参数变更（需停服）

> **执行窗口**：需停服。PG 重启会导致所有连接断开，应用必须先停止。
>
> **来源**：I2 服务器 PG 配置。
>
> **执行顺序**：先做可热加载的参数（1.1），再做需重启的参数（1.2），最后重启 PG（1.3）。
>
> ⚠️ **本步失败必须停止，不要继续下一步。**

### 1.1 可热加载参数（ALTER SYSTEM + pg_reload_conf）

> 这些参数通过 `ALTER SYSTEM SET` 写入 `postgresql.auto.conf`，然后 `SELECT pg_reload_conf();` 热加载生效，无需重启 PG。

**执行命令**：

```bash
sudo -u postgres psql <<'SQL'
-- ── 内存与查询规划 ──
ALTER SYSTEM SET work_mem = '8MB';
ALTER SYSTEM SET maintenance_work_mem = '512MB';
ALTER SYSTEM SET effective_cache_size = '10GB';

-- ── autovacuum 全局 ──
ALTER SYSTEM SET autovacuum_max_workers = '4';
ALTER SYSTEM SET autovacuum_naptime = '30s';
ALTER SYSTEM SET autovacuum_vacuum_scale_factor = '0.05';
ALTER SYSTEM SET autovacuum_analyze_scale_factor = '0.02';

-- ── WAL / checkpoint ──
ALTER SYSTEM SET max_wal_size = '4GB';
ALTER SYSTEM SET min_wal_size = '512MB';
ALTER SYSTEM SET checkpoint_completion_target = '0.9';

-- ── 日志 ──
ALTER SYSTEM SET log_min_duration_statement = '80';
ALTER SYSTEM SET log_timezone = 'UTC';

-- ── 时区 ──
ALTER SYSTEM SET timezone = 'UTC';

-- ── 观测 ──
ALTER SYSTEM SET track_io_timing = 'on';

-- 热加载生效
SELECT pg_reload_conf();
SQL
```

**预期输出**：

```
ALTER SYSTEM
ALTER SYSTEM
...（每行一个 ALTER SYSTEM）
 pg_reload_conf
----------------
 t
(1 row)
```

**验证命令**：

```bash
sudo -u postgres psql <<'SQL'
SELECT name, setting, unit, source
FROM pg_settings
WHERE name IN (
  'work_mem', 'maintenance_work_mem', 'effective_cache_size',
  'autovacuum_max_workers', 'autovacuum_naptime',
  'autovacuum_vacuum_scale_factor', 'autovacuum_analyze_scale_factor',
  'max_wal_size', 'min_wal_size', 'checkpoint_completion_target',
  'log_min_duration_statement', 'log_timezone', 'timezone',
  'track_io_timing'
)
ORDER BY name;
SQL
```

**预期验证输出**：

```
             name             | setting | unit |  source
------------------------------+---------+------+-----------
 autovacuum_analyze_scale_factor | 0.02   |      | configuration file
 autovacuum_max_workers          | 4      |      | configuration file
 autovacuum_naptime              | 30     | s    | configuration file
 autovacuum_vacuum_scale_factor  | 0.05   |      | configuration file
 checkpoint_completion_target    | 0.9    |      | configuration file
 effective_cache_size            | 10240  | 8kB  | configuration file
 log_min_duration_statement      | 80     | ms   | configuration file
 log_timezone                    | UTC    |      | configuration file
 maintenance_work_mem            | 512    | kB   | configuration file
 max_wal_size                    | 4096   | MB   | configuration file
 min_wal_size                    | 512    | MB   | configuration file
 timezone                        | UTC    |      | configuration file
 track_io_timing                 | on     |      | configuration file
 work_mem                        | 8192   | kB   | configuration file
(14 rows)
```

> 注意：`source` 列应为 `configuration file`（来自 `postgresql.auto.conf`），而非 `default`。`setting` 列的值可能以内部单位显示（如 `work_mem` 的 8192 kB = 8MB），属正常。

**失败处置**：
- 若某条 `ALTER SYSTEM` 报错：记录错误信息，其余参数仍可继续设置。最后查看 `pg_settings` 确认哪些未生效。
- 若 `pg_reload_conf()` 返回 `f`：检查 PG 日志 `sudo journalctl -u postgresql --since "5 min ago"` 查看加载失败原因。
- **回滚**：`ALTER SYSTEM RESET <param>;` 逐项重置为默认值，再 `SELECT pg_reload_conf();`。

- [ ] 已确认 14 项热加载参数全部生效（source = configuration file）

### 1.2 需重启参数（ALTER SYSTEM 写入，重启后生效）

> 以下 3 项参数写入后需重启 PG 才能生效。

**执行命令**：

```bash
sudo -u postgres psql <<'SQL'
-- shared_buffers = 3GB（PG 共享内存缓冲池，需重启）
ALTER SYSTEM SET shared_buffers = '3GB';

-- wal_buffers = 16MB（WAL 日志缓冲，需重启）
ALTER SYSTEM SET wal_buffers = '16MB';

-- shared_preload_libraries = pg_stat_statements（需重启，为第 3 步做准备）
ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statements';

SELECT pg_reload_conf();
SQL
```

**预期输出**：

```
ALTER SYSTEM
ALTER SYSTEM
ALTER SYSTEM
 pg_reload_conf
----------------
 t
(1 row)
```

> 注意：`pg_reload_conf()` 会返回 `t`，但上述 3 项参数的 `pending_restart` 列为 `t`，表示需要重启才真正生效。

**验证命令**（重启前）：

```bash
sudo -u postgres psql -c "SELECT name, setting, pending_restart FROM pg_settings WHERE name IN ('shared_buffers', 'wal_buffers', 'shared_preload_libraries') ORDER BY name;"
```

**预期验证输出**（重启前）：

```
             name             | setting              | pending_restart
------------------------------+----------------------+----------------
 shared_buffers               | 3GB                  | t
 shared_preload_libraries     | pg_stat_statements   | t
 wal_buffers                  | 16MB                 | t
(3 rows)
```

> `pending_restart = t` 表示参数已写入但需重启生效。

**失败处置**：
- 若 `ALTER SYSTEM SET shared_buffers = '3GB'` 报错 `parameter "shared_buffers" cannot be changed without restarting`：这是正常的——`ALTER SYSTEM` 写入成功，只是提醒需重启。只要不报 `ERROR` 即可。
- 若报 `ERROR: could not access file "pg_stat_statements"`：说明 PG 17 的 contrib 包未安装。执行 `sudo apt install postgresql-contrib-17`（或对应包管理器）后重试。

- [ ] 已确认 3 项重启参数已写入（pending_restart = t）

### 1.3 重启 PostgreSQL

> ⚠️ **本步失败必须停止，不要继续下一步。**
>
> 必须先停应用，再重启 PG，避免应用侧连接风暴。

**执行命令**：

```bash
# 1. 停止应用（先停应用，避免 PG 重启时应用疯狂重连）
sudo systemctl stop purelyprofit-server

# 2. 确认应用已停
sudo systemctl status purelyprofit-server
# 预期：Active: inactive (dead)

# 3. 重启 PostgreSQL
sudo systemctl restart postgresql

# 4. 确认 PG 已恢复
sudo systemctl status postgresql
# 预期：Active: active (running)

# 5. 确认连接正常
sudo -u postgres psql -c "SELECT 1;"
# 预期：返回 1 行
```

**验证命令**（重启后确认 3 项参数生效）：

```bash
sudo -u postgres psql -c "SELECT name, setting, pending_restart FROM pg_settings WHERE name IN ('shared_buffers', 'wal_buffers', 'shared_preload_libraries') ORDER BY name;"
```

**预期验证输出**（重启后）：

```
             name             | setting              | pending_restart
------------------------------+----------------------+----------------
 shared_buffers               | 3GB                  | f
 shared_preload_libraries     | pg_stat_statements   | f
 wal_buffers                  | 16MB                 | f
(3 rows)
```

> `pending_restart = f` 表示参数已生效。`setting` 应显示新值。

**失败处置**：
- 若 PG 重启后无法启动：
  - 检查日志：`sudo journalctl -u postgresql --since "5 min ago"`
  - 常见原因：`shared_buffers = 3GB` 超过可用共享内存（16G 机器不会出现，但小内存机器会）
  - 回滚：编辑 `/var/lib/postgresql/17/main/postgresql.auto.conf`（或对应路径），删除或注释 `shared_buffers` / `wal_buffers` / `shared_preload_libraries` 行，重启 PG。
- 若 PG 启动但 `shared_preload_libraries` 未生效：
  - 确认 `pg_stat_statements` 扩展文件存在：`ls /usr/lib/postgresql/17/lib/pg_stat_statements.so`
  - 若文件不存在：`sudo apt install postgresql-contrib-17` 安装 contrib 包后重启 PG。
- 若应用停止后无法重新启动：见第 4 步 systemd 更新。

> **注意**：此时应用处于停止状态。第 2~3 步可以在此间隙执行（PG 已恢复，应用已停），然后第 4 步更新 systemd 并重启应用。

- [ ] 已确认 PG 重启后 3 项参数全部生效（pending_restart = f）
- [ ] 已确认 PG 连接正常（SELECT 1 成功）

## 第 2 步：逐表 autovacuum 覆盖（可在线）

> **执行窗口**：可在线（PG 已恢复运行，应用可停可不停）。
>
> **来源**：I2 的 5 张表逐表 autovacuum 覆盖。
>
> 这些参数通过 `ALTER TABLE ... SET (...)` 生效，无需重启 PG。

**执行命令**：

```bash
sudo -u postgres psql <<'SQL'
-- ── 5 张写热点 / 大表的 autovacuum 覆盖 ──

-- 1. scan_orders：日增 10 万行，version+1 致 HOT 更新失败，高 dead tuple
ALTER TABLE scan_orders SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_analyze_scale_factor = 0.01,
  autovacuum_vacuum_insert_scale_factor = 0.05
);

-- 2. marketing_customers：balance/points/totalSpent 高频 UPDATE + 14 索引致 HOT 率低
ALTER TABLE marketing_customers SET (
  autovacuum_vacuum_scale_factor = 0.03,
  autovacuum_analyze_scale_factor = 0.01,
  autovacuum_vacuum_insert_scale_factor = 0.05
);

-- 3. space_sessions：长事务持锁，需更频繁 vacuum
ALTER TABLE space_sessions SET (
  autovacuum_vacuum_scale_factor = 0.05,
  autovacuum_analyze_scale_factor = 0.02
);

-- 4. audit_logs：纯追加，索引持续增长
ALTER TABLE audit_logs SET (
  autovacuum_vacuum_scale_factor = 0.05,
  autovacuum_analyze_scale_factor = 0.02,
  autovacuum_vacuum_insert_scale_factor = 0.05
);

-- 5. idempotency_records：纯追加，TTL 24h
```

## 第 6 步：归档任务首次启用（需低峰期）

### 6.1 为什么建议低峰期首次启用

归档任务（`sale-order-items-archive`）是一个 BullMQ repeatable job，每 24h 执行一次。首次启用时，如果 `sale_order_items` 表中已有超过保留窗口（默认 365 天）的数据，会触发大批量迁移：
- 单次任务最多 200 批 × 5000 行/批 = 100 万行
- 预估耗时约 20 秒（100 万行 INSERT+DELETE）
- 每批一个短事务（< 2s），不会产生长锁

由于当前服务器**尚未上线，无生产数据**，首次执行时 `sale_order_items` 表为空（或仅有少量测试数据），迁移量为 0，可安全在任何时间启用。

### 6.2 确认归档任务已注册



> 该日志行在应用启动时输出一次，表示 repeatable job 已注册到 Redis。

**失败处置**：
- 若无该日志行：
  - 检查 `production.env` 中 `APP_ARCHIVE_SALE_ORDER_ITEMS_ENABLED` 是否被设为 `false`（默认 `true`）
  - 若被禁用，设为 `true` 或删除该行后重启应用
  - 检查 Redis 连接是否正常

### 6.4 首次执行时间过长的处置

若首次执行时间超过 60 秒（通常意味着有大量超过 365 天的数据）：

1. **不要中断**——归档任务设计为可断点续传，即使中断下次也会从游标继续
2. 观察日志中的 `elapsedMs` 和 `totalArchived`，确认进度在推进
3. 单次任务最多 200 批（100 万行），到达上限后自动停止，24h 后继续
4. 若需要加快迁移，可临时缩短调度间隔（在 `production.env` 中设 `APP_ARCHIVE_SALE_ORDER_ITEMS_INTERVAL_MS=3600000` 即 1h，迁移完毕后改回 86400000）

**失败处置**：
- 若归档任务报错（日志出现 `[sale-order-items-archive-processor] failed`）：
  - 查看错误详情：`sudo journalctl -u purelyprofit-server --since "10 min ago" --no-pager | grep -A 5 "sale-order-items-archive.*failed"`
  - 常见原因：归档表未建（回到第 5 步执行 migration）、DB 连接超时
  - 修复后 BullMQ 会自动重试（默认重试策略）
- **回滚归档任务**：
  ```bash
  # 1. 禁用归档任务（在 production.env 中添加）
  echo 'APP_ARCHIVE_SALE_ORDER_ITEMS_ENABLED=false' >> /etc/purelyprofit-server/production.env

  # 2. 重启应用
  sudo systemctl restart purelyprofit-server

  # 3. 清理 Redis 中的 repeatable job 元数据（通过 redis-cli）
  redis-cli
  # 在 redis-cli 中：
  ```

## 第 7 步：上线后 7 天观测（可在线）

> **执行窗口**：可在线。应用已正常运行，开始持续观测。
>
> **来源**：I8 压测与上线的 7 天观测计划。
>
> **观测周期**：从第 4 步应用重启成功后开始计时，持续 7 天。

### 7.1 P0 告警（立即处置）

以下 3 项指标触发时，需要立即排查并可能回滚相关变更。

#### P0-1：PG 连接数 > 100

**采集命令**：

```bash
sudo -u postgres psql -c "SELECT count(*), state FROM pg_stat_activity GROUP BY state ORDER BY count DESC;"
```

**告警阈值**：`count` 总和 > 100（即接近或超过 `max_connections`）。

**处置**：
- 查看哪些连接占用量大：`SELECT application_name, state, count(*) FROM pg_stat_activity GROUP BY application_name, state ORDER BY count DESC;`
- 若应用连接过多（应 ≤ 80 = 4 workers × 20 poolMax）：检查是否有连接泄漏，确认 `prisma.service.ts` 的池推导取 min 修复是否生效
- 紧急情况可终止 idle 连接：`SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'idle' AND query_start < now() - interval '10 minutes';`

#### P0-2：PoolTimeout / connection timeout 日志

**采集命令**：

```bash
sudo journalctl -u purelyprofit-server --since "1 hour ago" --no-pager | grep -iE "PoolTimeout|connection timeout|prisma.*error.*connect"
```

**告警阈值**：出现任何 `PoolTimeout` 或 `connection timeout` 日志。

**处置**：
- 确认 PG 连接数是否达上限（P0-1）
- 确认是否有长事务持锁（`SELECT pid, now() - xact_start AS duration, query FROM pg_stat_activity WHERE state = 'active' AND xact_start IS NOT NULL ORDER BY duration DESC;`）
- 确认 `statement_timeout` 是否过短（应 10000ms）

#### P0-3：慢 SQL P95 > 300ms

**采集命令**：

```bash
sudo -u postgres psql -d purelyprofit <<'SQL'
SELECT
  percentile_cont(0.95) WITHIN GROUP (ORDER BY mean_exec_time) AS p95_ms,
  percentile_cont(0.99) WITHIN GROUP (ORDER BY mean_exec_time) AS p99_ms,
  count(*) AS total_queries
FROM pg_stat_statements
WHERE query NOT LIKE '%pg_stat_statements%';
SQL
```

**告警阈值**：`p95_ms > 300`。

**处置**：
- 查看最慢的查询：`SELECT query, mean_exec_time, calls, total_exec_time FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10;`
- 应用层慢 SQL 日志（80ms 阈值）：`sudo journalctl -u purelyprofit-server --since "1 hour ago" --no-pager | grep "\[slow-query\]"`

### 7.2 P1 指标（关注但不立即回滚）

以下 9 项指标需每日检查一次，异常时记录并评估是否需要处置。

#### P1-1：慢请求 > 800ms

```bash
sudo journalctl -u purelyprofit-server --since "24 hours ago" --no-pager | grep "\[slow-request\]" | wc -l
```

> 日志中 `[slow-request]` 出现次数。少量可接受，持续增长需排查。

#### P1-2：锁等待 > 5

```bash
sudo -u postgres psql -c "SELECT count(*) FROM pg_locks WHERE NOT granted;"
```

> `count > 5` 时排查持锁事务。

#### P1-3：IOPS await > 20ms

```bash
# 需要 iostat 工具
iostat -x 1 3 | grep -A 5 "Device"
```

> `await` 列 > 20ms 时说明磁盘积压。若无 `iostat`，安装 `sysstat` 包。

#### P1-4：缓存命中率 < 80%

```bash
sudo -u postgres psql -d purelyprofit <<'SQL'
SELECT
  sum(blks_hit) AS hit,
  sum(blks_read) AS read,
  round(100.0 * sum(blks_hit) / nullif(sum(blks_hit) + sum(blks_read), 0), 2) AS hit_rate_pct
FROM pg_stat_database
WHERE datname = current_database();
SQL
```

> `hit_rate_pct < 80` 时需排查是否索引未生效或缓存配置不足。

#### P1-5：Redis 内存 > 900MB

```bash
redis-cli INFO memory | grep used_memory_human
```

> Redis maxmemory 设为 1GB（I2 配置），> 900MB 时需排查 key 增长。

#### P1-6：Node 内存 > 800MB / worker

```bash
# 查看各 worker 进程内存
ps aux | grep "cluster-main" | grep -v grep
```

> 每个 worker RSS > 800MB 时需排查内存泄漏。--max-old-space-size=1024 限制 V8 老生代 1GB。

#### P1-7：retention-cleanup 未按期执行

```bash
sudo journalctl -u purelyprofit-server --since "24 hours ago" --no-pager | grep "retention-cleanup.*completed"
```

> 预期每 6h 出现 idempotency 清理日志、每 24h 出现 audit_logs 清理日志。若 24h 内无任何 retention-cleanup 日志，需排查 BullMQ worker 是否正常。

#### P1-8：归档任务未按期执行

```bash
sudo journalctl -u purelyprofit-server --since "24 hours ago" --no-pager | grep "sale-order-items-archive.*completed"
```

> 预期每 24h 出现归档任务完成日志。若无，检查 `APP_ARCHIVE_SALE_ORDER_ITEMS_ENABLED` 是否为 true。

#### P1-9：autovacuum 死元组 > 5000

```bash
sudo -u postgres psql -d purelyprofit <<'SQL'
SELECT
  relname,
  n_dead_tup,
  n_live_tup,
  round(100.0 * n_dead_tup / nullif(n_live_tup, 0), 2) AS dead_pct,
  last_autovacuum,
  last_autoanalyze
FROM pg_stat_user_tables
WHERE n_dead_tup > 5000
ORDER BY n_dead_tup DESC
LIMIT 10;
SQL
```

> `n_dead_tup > 5000` 的表需要关注。若 `last_autovacuum` 为空且 dead tuple 持续增长，手动执行 `VACUUM ANALYZE <table>;`。

### 7.3 7 天观测小结清单

每天检查以下各项并记录：

- [ ] 第 1 天：PG 连接数 / PoolTimeout / 慢 SQL P95 / 缓存命中率 / Redis 内存 / Node 内存 / retention-cleanup / 归档任务 / dead tuple
- [ ] 第 2 天：同上
- [ ] 第 3 天：同上
- [ ] 第 4 天：同上
- [ ] 第 5 天：同上
- [ ] 第 6 天：同上
- [ ] 第 7 天：同上，汇总 7 天趋势

> 7 天内若所有 P0 指标均未触发，P1 指标均在阈值内，则判定上线成功。
