## 第 3 批：分区决策（只出决策，不写代码）

| 项 | 内容 |
| --- | --- |
| 打开 | `03-partition-decision.full.md` |
| 占位 | 1 个：`<I3 上游摘要>` |
| 前置 | 无（可与第 2 批并行） |
| 改什么 | **什么都不改**，只出方案对比 |
| 落盘 | `实施/notes.md` → `## I3 分区决策` |

**为什么要单独一批**：分析阶段判定 `sale_order_items` / `audit_logs`「档 B 必须分区」，
但 PostgreSQL 要求分区表的主键包含分区键。若这两张表当前主键是单列 `id`，
分区就意味着 `@id` 要改成 `@@id([id, createdAt])`，**Prisma Client 的 API 会跟着变**，
直接违反「不得修改业务语义与接口契约」这条硬约束。

所以必须先搞清楚：分区到底能不能做？如果不能，归档冷热分离能不能达到同样效果？

**你现在没上线、零数据，是做分区成本最低的时刻**——过这个村没这个店。这一批的结论要给足重视。

systemd 还是旧的、4 个 migration 没跑、扩展没建。

**AI 连不上你的服务器**，所以这一批的产物是「照着敲」的执行手册，
由你登录服务器逐条执行。手册会覆盖 8 个步骤：

```
第 0 步  前置确认（PG 版本 / max_connections / 磁盘 / 当前连接数 / systemd 是否同步）
第 1 步  PG 参数变更（按是否需重启分组）
第 2 步  逐表 autovacuum 覆盖
第 3 步  pg_stat_statements 扩展
第 4 步  systemd 更新与应用重启
第 5 步  执行 4 个 migration（低峰期）
第 6 步  归档任务首次启用
第 7 步  上线后 7 天观测
第 8 步  压测执行
```

每一步都会包含：**执行命令 / 预期输出 / 验证命令 / 失败处置**，
并标注是「可在线 / 需低峰期 / 需停服」。

## 顺序与依赖

```
批1 参数 ──┬─→ 批2 服务器PG        （批2 需要批1 的连接数结论）
           │
批3 分区决策（独立，可先做，因为它可能要改批4/批5的范围）
批4 索引处置 ──→ 批5 索引新增      （同表索引改动要串行，别并行）
批6 代码改写（多轮，独立）
批7 缓存清理（独立）
批8 压测上线 ← 依赖批1~批7 全部完成
```

**建议实际执行顺序**：`批3 → 批1 → 批2 → 批4 → 批5 → 批6 → 批7 → 批8`

理由：先把分区这个最大的不确定性问清楚，它会决定索引改动要不要等、要不要重做。
批 1/2 是参数，随时可做。索引类改动放一起避免打架。

## 三条纪律

1. **每批先看计划，再让它动手**。卡里写了「等我确认后再执行」，你确认前它不该改文件。
2. **验收要看校验结果**。每批交完必须包含 `check-f0rest-rules.mjs` exit=0 和 `pnpm run typecheck` 通过，两个都要看到。
3. **改完就提交一次 git**。8 批 = 至少 4 个 commit，出问题好回滚。

## 出错怎么判断

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| AI 只贴代码不改文件 | 没理解"要落地" | 回一句「用编辑工具真正写入文件，不要只在对话里贴代码」 |
| 它一次想改 8 项 | 范围失控 | 回一句「本批只做指定的前 3 项，其余等我下一批指令」 |
| 它顺手重构了无关代码 | 违反最小改动 | 让它 `git checkout` 那个文件，只保留本批必要改动 |
| 迁移脚本想改已有的 migration 文件 | 违反硬约束 b | 立刻叫停，要求只新增目录 |
| 没跑校验就交差 | 偷懒 | 回一句「先跑 check-f0rest-rules 和 typecheck，贴出 exit code」 |
| 涉及金额的改写没给一致性验证 | 红线 | 回一句「给出金额数值一致性验证的可执行步骤，否则本项不通过」 |
